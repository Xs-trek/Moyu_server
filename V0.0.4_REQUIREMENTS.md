# Moyu v0.0.4 requirement memory

Status: approved for implementation on 2026-08-21. Dynamic Web UI validation remains a user
acceptance step; repository-side verification is static, contract, unit, integration and build
verification.

This document is the scope authority for v0.0.4. If implementation and this document disagree,
the implementation is incomplete until either it is corrected or the user approves a requirement
change here.

## V004-CORE-001 — preserve the native-runtime boundary

Moyu keeps its own Android/WebView-to-gateway protocol and EasyTier transport. Claude Code, Codex
and OpenCode make model/provider requests from their existing PC-native CLI/runtime. Moyu does not
add a provider SDK, call an AI provider directly, perform provider probes, copy credentials to the
phone or inject a Moyu/phone marker into model input.

The OpenCode JS SDK, when used, is only a generated localhost client for the official OpenCode
Server API. It is not a model-provider SDK and must not start a second hidden runtime.

## V004-ARCH-001 — one public adapter contract

Claude Code, Codex and OpenCode expose Session, Message, Event, Approval, History, Resume and
Interrupt through the common adapter contract. Platform-specific parsing, model syntax, approval
translation and process/server control stay inside `src/adapters/<adapter>/` or its adapter-owned
bridge. Public REST, WebSocket and SessionManager code must not branch on a platform name.

Runtime adapters and the optional PTY transport are separate concepts. Resume references are
opaque adapter-owned strings, distinct from Moyu's internal session id. Legacy `cliSessionRef` and
`nativeSessionId` projections may remain for one compatibility window but cannot be accepted as a
phone-controlled session-creation escape hatch.

## V004-OC-001 — official shared OpenCode server

OpenCode uses the official `opencode serve` Server API. Moyu does not parse OpenCode SQLite, depend
on Desktop private sidecars or invent a second OpenCode control protocol.

Exactly one OpenCode server connection is shared by Moyu sessions:

- managed mode starts one loopback `opencode serve` process owned by Moyu;
- attach mode connects to one pre-existing loopback server and never owns or stops it;
- OpenCode Desktop/TUI may attach to the same backend at the same time;
- init generates and privately persists a stable managed-Server credential so Desktop/TUI setup
  is one-time; provider/model/API-key configuration remains entirely OpenCode-owned;
- per-session dispose unregisters the Moyu handle and does not stop the shared server;
- Moyu only terminates a managed child during gateway shutdown;
- credentials and server URL remain PC-local and are never remotely patchable or returned to the
  phone.

Health/version and the required Session, Message, Event, Permission and Abort surfaces are checked
before the adapter becomes available. Unsupported versions fail closed inside the OpenCode adapter
instead of triggering guessed route fallbacks.

## V004-CC-001 — preserve Claude Code behavior

Claude Code keeps the approved `claude -p` / `stream-json` / hooks route, including Plan, Auto and
Accept Edits, model switching, profile selection, approval fail-closed behavior and v0.0.3 event
semantics. v0.0.4 does not expand Claude Code product features.

## V004-CODEX-001 — preserve Codex behavior

Codex keeps the approved `codex exec --json` and native resume route, including OAuth, API-key and
third-party Responses-compatible URL profiles. Its supported CLI/protocol range remains an
adapter-local compatibility gate. v0.0.4 does not chase unrelated upstream features.

## V004-UI-001 — capability-driven clients

Backend status/config/schema, Android projection and Web UI contract use the same adapter
capabilities. Platform lists, create controls, Profile, model, effort/mode, attachments, approval,
history, resume, interrupt and status presentation are driven by capability data. Adding OpenCode
must not add platform-name conditionals to common Session UI, message rendering, reconnect or error
handling.

Platform display metadata and local icons live in one presentation registry. An unknown adapter
uses a neutral accessible fallback and is never presented as Claude Code, Codex or OpenCode.

## V004-COMPAT-001 — additive wire compatibility and fail-closed handshake

The v0.0.4 product version keeps Moyu wire protocol version 1 while changes remain additive. The
backend reports the protocol version; Android validates it and forwards the real value instead of
fabricating it. An unsupported protocol or adapter protocol version is reported as unavailable or
incompatible, not silently coerced.

Each adapter has recorded protocol fixtures and a shared conformance suite covering create/send,
streaming messages, approvals, interrupt, history, resume, failure and dispose. OpenCode additionally
covers managed/attach ownership, one-server-many-sessions, multi-client events, authentication,
loopback rejection, SSE reconnect and deduplication.

## V004-FUTURE-001 — reserve only a runtime source seam

The contract may distinguish a native CLI runtime from a shared local-server runtime. This is the
only v0.0.4 reservation for a future Local Chat source. No independent Chat, provider configuration
UI, cached offline editing workflow, complex Branch system or plugin framework is implemented.

## V004-SCOPE-001 — explicit exclusions

v0.0.4 does not implement Local Chat, a fourth platform, EasyTier kernel trimming, an OpenCode
database reader, an OpenCode Desktop sidecar dependency, provider SDK calls or arbitrary remote
OpenCode Server URLs.

## V004-REL-001 — release candidate gate

The candidate identifies as backend/UI/Android `0.0.4`, Android `versionCode 4`, and Moyu protocol
version 1. Before user handoff it must pass backend typecheck/unit/integration/provider-surface and
build gates, frontend build/static checks, Android unit tests/lint/release build, and APK
identity/content/signature inspection. A smoke against a real local OpenCode Server is required
before claiming formal OpenCode release compatibility. Attach mode does not require an OpenCode
executable; managed-mode smoke additionally requires a supported executable capable of starting
`opencode serve`. Any unexercised real-runtime mode must remain explicit in the handoff.
