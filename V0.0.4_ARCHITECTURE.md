# Moyu v0.0.4 aggregation architecture

This document describes the v0.0.4 implementation boundary. `V0.0.4_REQUIREMENTS.md` remains the
scope authority; this document maps that scope to modules and data flow.

## Stable control plane

```text
Android WebView
  -> window.MoyuHost (versioned UI intents)
  -> Android native state/cache/transport
  -> EasyTier overlay
  -> Moyu REST + WebSocket protocol v1
  -> SessionManager
  -> Adapter contract
```

The control plane owns authentication, sequencing, replay, local cache projection and user
approvals. It never becomes a model-provider client. Adapter events are the only boundary between
runtime-specific protocols and common Session state.

## Runtime sources

| Adapter | Runtime source | Native control protocol | Ownership |
| --- | --- | --- | --- |
| Claude Code | `native-cli` | `claude -p --stream-json` plus native hooks | process per active turn/session |
| Codex | `native-cli` | `codex exec --json` plus native hooks | process per active turn/session |
| OpenCode | `local-server` | official OpenCode Server REST/SSE API | one shared managed or attached server |

`runtime.source` is a small descriptive seam required by OpenCode. It does not register Local Chat
or make runtime sources dynamically loadable.

## Public adapter contract

The shared contract in `src/adapters/types.ts` owns:

- Session creation and a runtime handle;
- normalized Message and AdapterEvent values;
- send, interrupt, approval resolution and disposal;
- adapter-owned opaque `resumeRef` values;
- optional History list/read/resume providers;
- runtime, streaming, attachment, approval and configuration capabilities;
- an adapter-local compatibility report.

`AdapterManager` is the registry and history aggregator. `SessionManager` owns internal UUIDs,
bounded memory, source-id upserts, event sequence/replay, pending approvals and turn state. Neither
module may inspect a platform name.

Claude/Codex JSONL discovery remains in the existing read-only native-history parser but is exposed
through an adapter-owned History provider. OpenCode History calls its official Session/Message API;
it never reads OpenCode storage.

## Resume identity

`sessionId` is Moyu's internal UUID. `resumeRef` is an opaque, bounded string issued and validated
by an adapter. A fresh runtime publishes it only when the upstream runtime has created a real
resumable identity. The phone-facing create route cannot supply a resume reference; only a trusted
History resume route can bind one.

`cliSessionRef` and `nativeSessionId` are v0.0.3 response aliases for one compatibility window.
Common code must not parse them or assume UUID syntax.

## OpenCode shared server

The OpenCode adapter owns three layers:

1. a server runtime handling managed/attach lifecycle, ownership, compatibility and one global SSE
   connection;
2. a bounded loopback-only client for the official REST/SSE endpoints;
3. lightweight Session handles that map official messages, parts, permissions and status into the
   common contract.

The client intentionally keeps a small adapter-local HTTP surface instead of exposing generic
fetch to the rest of Moyu. This permits hard enforcement of loopback HTTP, disabled redirects,
bounded response/SSE frames, Basic Auth and safe error projection. Its routes and payloads are
fixtures of the official OpenCode Server API rather than a Moyu-defined OpenCode protocol.

### Managed mode

- Moyu starts exactly one `opencode serve --hostname 127.0.0.1 --port ...` child.
- All Session handles use that server and select their working directory through the official
  directory parameter.
- Moyu verifies the child it started remains the endpoint owner.
- `moyu -init` generates a stable Basic-auth password in Moyu's private PC config. This enables
  OpenCode Desktop/TUI to be configured once as another client of the same Server; the secret is
  never included in phone-facing config or patch surfaces.
- Gateway shutdown terminates the owned child; Session disposal does not.

### Attach mode

- Moyu accepts only a PC-local HTTP loopback URL from local configuration.
- Moyu does not require an OpenCode binary, start a process or terminate the server.
- Basic Auth uses PC process environment/local configuration and is never sanitized to the phone.
- OpenCode Desktop/TUI may attach to the same endpoint.
- Desktop's built-in sidecar is not an attach target because it generates a private random
  password on each launch. Moyu detects the application for setup guidance but never reads its
  private store, IPC state or database.

### Events and reconciliation

One global event stream is demultiplexed by upstream Session id. Official message, part and call ids
form stable `sourceId` values. `message.upsert` lets SessionManager and Android replace an existing
timeline record instead of duplicating it when:

- REST history and SSE overlap;
- the SSE stream reconnects;
- an OpenCode Desktop client creates or updates a message;
- a tool part changes from pending to completed/error.

After reconnect, bound handles reconcile the official Session messages before consuming further
events. Moyu maintains one in-flight input per Session, but OpenCode SSE remains authoritative when
another client acts on the same Session.

## OpenCode control mapping

```text
Common operation          Official OpenCode operation
create                    POST /session
send                      POST /session/:id/prompt_async
history / reconcile       GET  /session/:id/message
interrupt                 POST /session/:id/abort
approval allow            response = once
approval allow_session    response = always
approval deny             response = reject
events                    GET /global/event (SSE)
health/version            GET /global/health
```

OpenCode model selection remains adapter-local: a public `provider/model` string is split into the
official `{providerID, modelID}` request shape. Empty input inherits OpenCode's native default.

## Client projection

`GET /server/info` is the source for protocol version, global features and adapter status. Android
validates the protocol before syncing and projects adapter capabilities without platform branches.
The Web UI renders the server adapter list and the active adapter's capabilities. A local
presentation registry supplies display names/icons only; it cannot change behavior.

Account/Profile switching remains an optional Claude/Codex capability. OpenCode credentials and
providers stay owned by OpenCode, so `accountProfiles=false` is a valid common state rather than a
special UI case.

## Compatibility policy

- Moyu wire protocol remains version 1 while changes are additive.
- Claude and Codex retain their existing adapter-local version/protocol checks.
- OpenCode v0.0.4 targets Server API 1.17.9 through 1.18.x, with recorded 1.18.19 fixtures and
  isolated real-runtime smokes against both 1.17.9 and 1.18.19.
- An adapter with an unsupported version or missing required surface reports incompatible and does
  not become selectable.
- Mock protocol fixtures exercise parsing; a real local OpenCode server smoke verifies health,
  lifecycle, Session, History and Abort without making a provider request.

## Fourth-platform test

A future fourth platform should require only:

- `src/adapters/<new>/` and one registry/default-config entry;
- adapter protocol fixtures, conformance tests and a real smoke;
- an optional adapter History/Profile implementation when genuinely supported;
- one client presentation metadata/icon entry and fixture.

It must not require platform branches in SessionManager, REST/WS, EasyTier, Android database/view
mapping, common message/approval rendering or reconnect behavior. Needing such a branch is evidence
that this architecture has regressed.
